Origem: revisão completa da aplicação identificou bugs reais na v1.7.2.

SUB-FASE 6.1 — BUGS CRÍTICOS DE COMPORTAMENTO
  Impacto: Crítico  |  Complexidade: Mínima  |  Modelo: Sonnet 4.6

  [C1] 📋 Rides.renderCalendar() e TrainingLog.refresh() inexistentes
       Arquivo: js/strava.js (linha ~104) e js/garmin.js (linha ~155)
       Impacto: Após sync Strava/Garmin, UI NÃO atualiza calendário
                nem training log — usuário precisa de hard reload para
                ver os dados importados.
       Fix: Trocar por Rides.render() e remover TrainingLog.refresh()
            (função não existe no módulo).

  [C2] 📋 Memory leak no gráfico de zonas FC
       Arquivo: js/activities.js (linha ~406)
       Impacto: A cada re-render sem dados de FC, o Chart.js anterior
                não é destruído. Acumula objetos na memória e pode
                causar flickering ou erro "canvas already in use".
       Fix: Adicionar _zoneChart.destroy() antes de substituir innerHTML.

  [C3] 📋 Falsy-zero em validação de peso
       Arquivo: js/app.js (linhas ~210 e ~263)
       Impacto: if(!peso) rejeita 0 como inválido. Padrão perigoso
                que pode mascarar outros campos numéricos no futuro.
       Fix: Substituir por isNaN(peso) || peso <= 0.

SUB-FASE 6.2 — BUGS DE SEGURANÇA
  Impacto: Alto  |  Complexidade: Mínima  |  Modelo: Sonnet 4.6

  [S1] 📋 Token Strava impresso em plaintext nos logs
       Arquivo: server/services/strava.js (linhas 48-49)
       Impacto: Qualquer pessoa com acesso ao journalctl ou logs
                capturados consegue o refresh_token completo.
       Fix: Mascarar token: t.slice(0,6) + '****' + t.slice(-4)

  [S2] 📋 Timing attack na autenticação
       Arquivo: server/routes/auth.js (linhas ~24-31)
       Impacto: Username errado retorna em <1ms; username certo +
                senha errada demora ~100ms (bcrypt). Atacante mede
                tempo e confirma username válido sem brute force.
       Fix: Sempre executar bcrypt.compare() independente do username:
            const ok = user === config.ADMIN_USER
                    && await password.verify(pass, config.ADMIN_PASS_HASH);

  [S3] 📋 DELETE global sem validação mínima em bulk operations
       Arquivos: server/routes/modes.js, workouts.js, home-exercises.js
       Impacto: PUT com array vazio [] apaga todos os modos/workouts/
                exercícios permanentemente. Dados órfãos e perda total.
       Fix: Rejeitar array vazio com 400 antes do DELETE.

SUB-FASE 6.3 — BUGS DE QUALIDADE
  Impacto: Médio  |  Complexidade: Baixa  |  Modelo: Sonnet 4.6

  [Q1] 📋 Regressão linear distorcida com múltiplas pesagens por dia
       Arquivo: js/app.js (linhas ~404-450)
       Impacto: Se há 2 pesagens em 01/06, o ponto x=0 aparece duas
                vezes com pesos distintos, distorcendo o slope semanal
                e a previsão da meta.
       Fix: Consolidar por dia (média ou última pesagem) antes de
            calcular a regressão.

  [Q2] 📋 FileReader sem validação do data URI
       Arquivo: js/app.js (linha ~105)
       Impacto: split(',')[1] retorna undefined se o arquivo não
                for uma data URI válida; API recebe data: undefined
                e retorna erro genérico sem diagnóstico.
       Fix: Verificar parts.length === 2 antes de prosseguir.

  [Q3] 📋 updateHomeExercise retorna undefined em vez de false
       Arquivo: js/storage.js (linha ~355)
       Impacto: Inconsistência com updateWorkout (retorna true/false).
                Callers futuros podem fazer if(result) e se comportar
                inesperadamente.
       Fix: return false; em vez de return; no caso de id não encontrado.

  [Q4] 📋 Valores NaN e negativos não validados na UI de métricas
       Arquivo: js/activities.js (linha ~86)
       Impacto: Se backend retornar bike.km = NaN ou tempoMovS = -5000,
                UI renderiza "NaN km" e "-1h00min" sem aviso.
       Fix: Filtrar com isFinite(v) && v > 0 antes de renderizar.

SUB-FASE 6.4 — SEGURANÇA DEFENSIVA DO BACKEND
  Impacto: Médio  |  Complexidade: Baixa  |  Modelo: Sonnet 4.6

  [D1] 📋 bodyLimit global ausente no Fastify
       Arquivo: server/index.js
       Impacto: Apenas /api/user/avatar tem bodyLimit explícito. Rotas
                como /api/workouts e /api/rides aceitam payloads de
                tamanho ilimitado. Usuário autenticado pode causar DoS
                por consumo de memória.
       Fix: Definir bodyLimit global de 1MB no registro do Fastify:
            const fastify = require('fastify')({ ..., bodyLimit: 1048576 });

  [D2] 📋 Error detail leakage em rotas de sync
       Arquivos: server/routes/strava.js, garmin.js
       Impacto: { error: '...', detail: err.message } retorna mensagens
                internas do Strava/Garmin ao cliente (IDs internos,
                rate limit info, etc).
       Fix: Log completo no req.log.error; retornar só mensagem genérica.

  [D3] 📋 JSON corrompido no banco silencia o erro
       Arquivo: server/routes/profile.js (linhas 63, 169)
       Impacto: catch (_) { return {}; } mascara corrupção real.
                Usuário recebe dados vazios sem saber que algo falhou.
       Fix: Adicionar req.log.warn(e, 'payload corrompido') no catch.

STATUS GERAL: 📋 Planejado

Contexto: a tabela garmin_daily_health já tem passos, sono (total/deep/
light/REM), stress, body battery e HRV sincronizados. Os dados existem
mas nenhum relatório os utiliza. Esta fase cria a seção "Insights" com
análises de valor real para o atleta ciclista.

Dados disponíveis (já no banco):
  garmin_daily_health: passos, sono_*_s, stress_avg/max,
                       body_battery_max/drain, hrv_*_avg/status
  garmin_activities:   km, tempo, elevacao, fc_media, fc_max,
                       watts_avg, cadencia_avg, calorias
  weights:             historico de peso com fonte
  training_log:        dias treinados com tipos e payload

SUB-FASE 7.1 — ÍNDICE DE FADIGA SEMANAL  (prioridade 1)
  Impacto: Muito Alto  |  Complexidade: Média  |  Modelo: Opus 4.7
  Tabelas: garmin_daily_health
  Calcula: (BBI_drain/max × 0.40) + (HRV_delta × 0.35)
           + (stress_avg × 0.25) → score 0-100
  Exibe: "Recuperado — intensidade ok" / "Moderado" / "Descanse hoje"
  Onde: novo card no topo da seção Atividades (ou futura seção Insights)

SUB-FASE 7.2 — SONO × DESEMPENHO  (prioridade 2)
  Impacto: Alto  |  Complexidade: Média  |  Modelo: Opus 4.7
  Tabelas: garmin_daily_health + garmin_activities
  Calcula: Para cada atividade, busca sono_deep_s e sono_rem_s da
           noite anterior. Correlaciona com fc_media e km.
  Exibe: Gráfico de dispersão + alerta "Dormiu mal antes desta ride"
  Onde: Detalhes de cada atividade (futura seção Histórico)

SUB-FASE 7.3 — WATTS/KG SEMANAL  (prioridade 3)
  Impacto: Alto  |  Complexidade: Baixa  |  Modelo: Sonnet 4.6
  Tabelas: garmin_activities + weights
  Calcula: watts_avg / peso_do_dia por atividade → média semanal
           + trend % vs semana anterior via SQL LAG()
  Exibe: Sparkline 12 semanas + badge "Melhorando/Estável/Redução"
  Onde: Card na seção Atividades (Volume de Treino)

SUB-FASE 7.4 — CARGA AGUDA VS. CRÔNICA (TSS simplificado)  (prioridade 4)
  Impacto: Muito Alto  |  Complexidade: Alta  |  Modelo: Opus 4.7
  Tabelas: garmin_activities + garmin_daily_health
  Calcula: TSS ≈ (tempo_min × (fcMedia/fcMax)² × 100 / 60) por atividade
           ATL = média exponencial 7 dias, CTL = 42 dias
           TSB = CTL - ATL (positivo = fresco, negativo = acumulado)
  Exibe: Gauge visual + recomendação de tipo de treino para hoje
  Onde: Seção Insights ou card no Home

SUB-FASE 7.5 — CUSTO METABÓLICO POR KM  (prioridade 5)
  Impacto: Médio  |  Complexidade: Baixa  |  Modelo: Sonnet 4.6
  Tabelas: garmin_activities
  Calcula: calorias / (distancia_m / 1000) → kcal/km por atividade
           Baseline = média 90 dias, variação % semanal
  Exibe: Tendência com alerta "Eficiência reduzida — revisar técnica"
  Onde: Card na seção Atividades

SUB-FASE 7.6 — CORRELAÇÃO PESO × PERFORMANCE  (prioridade 6)
  Impacto: Médio  |  Complexidade: Média  |  Modelo: Opus 4.7
  Tabelas: weights + garmin_activities
  Calcula: Watts/kg por semana vs. peso médio da semana
           Alerta se perda > 2%/sem sem melhora de performance
           (indica perda muscular, não de gordura)
  Exibe: Gráfico dual-axis + recomendação nutricional
  Onde: Seção Perfil (abaixo da análise de peso)
